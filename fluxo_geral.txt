
Fluxo Geral do Projeto de Análise de Dados - Para o meu entendimendo

                                    Detecção de Fraudes

1. Definição do problema
    Antes do código, devo saber: o que estou tentando responder ou prever?
    Neste caso, "dado o histórico de transações, consigo identificar quais são fraudulentas?"
    Qual métrica importa? Durante a aula sobre o projeto, fizemos a análise do recall e acurácia, mas o recall é o que importa mais, porque deixar passar uma fraude é pior que investigar uma transação normal à toa.

2. Coleta dos Dados
    Neste projetos, coletamos os dados através de uma url="link", usando o pandas pd.readcsv(url).

3. Exploração inicial (EDA - Exploratory Data Analysis)
    Conhecendo os dados antes de mexer neles.
        - Quantas linhas/colunas? Tipos de dados?
        - Tem valores nulos, duplicados?
        - Qual a distribuição da variável alvo (Class)?
        - Como as variáveis se distribuem? Tem outliers?

4. Limpeza dos dados (Data Cleaning)
    Com base no que o EDA mostrou, agora posso:
        - Tratar valores nulos (remover, preencher com média/mediana, etc.)
        - Remover duplicados
        - Corrigir tipos de dados errados
        - Tratar outliers (decidir se são erro ou informação real — em fraude, muitas vezes o outlier é a fraude, então devo ter cuidado ao removê-los)

5. Feature Engineering (criação/transformação de variáveis)
    Aqui, posso criar novas colunas que ajudam o modelo a aprender melhor, ou transformar as existentes:
        - O Amount_log usado na aula (log da variável Amount, que ajuda a suavizar a assimetria da distribuição)
        - Amount_scaled (padronização)
        - Posso também acrescentar ao projeto: extrair hora do dia a partir de Time, criar variáveis de razão/proporção, etc.

6. Separação treino/teste
    Depois de preparar os dados, é preciso separar uma parte para "treinar" o modelo e outra para "testar" se ele realmente aprendeu (e não decorou). É o que fizemos na aula com train_test_split. Isso é feito antes de treinar qualquer modelo, nunca depois, senão o teste fica contaminado.

7. Balanceamento das classes (quando necessário)
    Como fraude é raro, o modelo tende a "preguiça": aprender a dizer sempre "não é fraude" e já acerta 99%+. Por isso, técnicas como SMOTE, undersampling ou class_weight="balanced" entram aqui. Depois do split, e aplicadas só no treino (nunca no teste, senão é como se estivéssimos "trapaceando").

8. Treinamento do modelo
    Aqui, posso escolher um ou mais algoritmos (Regressão Logística, Random Forest, XGBoost) e ensinar eles com os dados de treino. Geralmente testa-se mais de um modelo para comparar.

9. Avaliação do modelo 
    Depois de treinado, posso testar o modelo com dados que ele nunca viu (teste) e mede o desempenho:
        - classification_report (precision, recall, F1)
        - Curva ROC / AUC
        - Curva Precision-Recall (mais informativa que ROC quando as classes são desbalanceadas, como neste caso)

10. Ajuste fino (Threashold e Hiperparâmetros)
    - Threashold: por padrão, o modelo classifica como fraude se a probabilidade > 0.5, mas eu posso mudar esse corte (na aula, usamos threashold=0.3) para equilibrar melhor precision vs recall.
    - Hiperparâmetros: usar GridSearchCV para testar várias configurações do modelo e achar a que performa melhor.

11. Interpretação/Explicabilidade
    Um modelo "caixa preta" que só cospe previsões não é suficiente em ambientes profissionais - especialmente em fraude, onde você precisa justificar porque uma transação foi marcada. É aqui que entra o SHAP: ele mostra quais variáveis mais pesaram em cada decisão do modelo.

12. Comunicação dos resultados
    Depois de tudo pronto, o último passo é traduzir isso para quem não é técnico - dashboards, relatórios, apresentações. De nada adianta um modelo excelente se ninguém no negócio entende o impacto dele.
